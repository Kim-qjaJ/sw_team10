## NFR-001 응답 시간 (맥미니 서버, 실제 외부 API, TMAP 실제 길 거리 포함)

측정: 브라우저에서 /api/v1/recommend 호출, 질문마다 새 세션. 서버 기록(timing_ms.total_ms) 기준.

| 구분 | 횟수 | 결과 | 기준 |
|---|---|---|---|
| 사전으로 해석되는 질문(지역+종류), 첫 호출 | 20 | 105~804ms (평균 308ms) | 3초 이내 → 통과 |
| 같은 질문 다시 호출 | 10 | 118~203ms | 3초 이내 → 통과 |
| LLM이 해석하는 질문 (평가 세트) | 18 | 1.9~8.9초 | 30초 이내 → 통과 |
| 날씨 질문 (기상청 관측값으로 바로 답함) | 2 | 109~113ms | - |

- 11-16(120~368ms)보다 첫 호출이 느려진 것은 TMAP 경로 거리 조회(요청당 최대 0.46초)가 추가됐기 때문이다. 경로 결과는 5분간 저장해 같은 질문은 다시 빨라진다.
- 20건: 서면 카페, 해운대 맛집, 광안리 밥집, 기장 관광지, 전포동 맛집, 덕천 카페, 부산역 근처 약국, 서면 맛집이랑 카페, 남포동 카페, 센텀 맛집, 송정 카페, 동래 맛집, 영도 관광지, 연산동 카페, 사직동 맛집, 하단 카페, 부산대 맛집, 다대포 관광지, 수영 카페, 명지 맛집 (모두 route=local)
- Provider 대기 상한 provider_wait_seconds = 5.5초, TMAP 대기 상한 4초(요청 전체). 넘기면 그 결과 없이 응답한다.

## 추가 측정 (2026-11-21 저녁, 지연 시 응답 목표 시간 보완 뒤)

### NFR-001 정상 상태 (TMAP 실제 경로 포함, 경로 캐시가 빈 상태)

실제 서버(맥미니)에 Local Router 질의 20건을 서로 다른 지역으로 보냄. 모두 `route=local`, 결과 5곳.

| 항목 | 값 |
|---|---|
| total_ms 최소 / 평균 / 최대 | 211 / 598 / 1,143 ms |
| TMAP 경로 조회 | 16건 성공(대체 0곳), 4건은 군·구 단위라 기준점 없음(`no_origin`) |
| 판정 | 기준 3초 이내 통과 |

오전 측정(105~804ms, 평균 308ms)보다 느린 것은 이번에는 지역을 겹치지 않게 골라 경로 캐시를 쓰지 못했기 때문이다.

### NFR-001 지연 상태 (AC-014, TMAP 포함)

실제 서버에는 지연을 넣을 수 없어, 실제 설정값 그대로 파이프라인을 실행하는 시험으로 쟀다
(`tests/test_recommendation_performance.py::test_slow_provider_and_slow_tmap_still_answer_within_6_seconds`).

- 조건: 장소 Provider 2개 중 1개는 30초 동안 응답 없음, 날씨·지하철역 조회 3초, TMAP 경로 1건당 3초
- 설정: Provider 대기 5.5초, TMAP 예산 4초, 응답 목표 5.8초(`response_deadline_seconds`)

| 항목 | 값 |
|---|---|
| 응답 시간 | 5.67초 (search 5,514 · context 55 · routing 2 ms) |
| 결과 | 빠른 Provider 결과로 응답, 늦은 Provider는 `timeout`, 경로는 직선거리로 대체하고 안내 |
| 판정 | 기준 6초 이내 통과 |

보완 전에는 검색 대기(5.5초) 뒤에 날씨·경로 조회(최대 4초)를 그대로 기다려 최대 약 9.5초가 걸릴 수 있었다.
이제 검색이 늦어진 만큼 날씨·지하철역·TMAP 조회 시간을 줄인다.
